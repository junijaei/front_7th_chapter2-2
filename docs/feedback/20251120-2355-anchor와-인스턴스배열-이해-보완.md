## 이전 상황

사용자가 anchor의 개념과 필요성은 이해했지만, 코드 구현과의 연결에서 다음 질문들이 남아있음:

1. 새로운 인스턴스 배열의 순서가 어떻게 정해지는가?
2. 왜 역순으로 돌아도 마지막 태그가 맨 마지막에 가는가?
3. 제시된 코드가 왜 제대로 동작하는가?

---

## 사용자의 이해 내용 정리

### 사용자가 설명한 내용

> 1. 모든 렌더링 때마다 처음부터 시작돼. 최상단 부모를 탐색하다가, 자식 태그가 있다면 재귀적으로 호출되는 구조야.
>
> 2. 이때 Fragment는 여러개의 자식 태그를 가질 수 있어. 하나로 묶는거지.
>
> 3. 이 Fragment가 업데이트가 되면, dom도 새로운 위치에 넣어야 할 때가 있는데, host처럼 부모 태그(=dom)가 명확하게 위치한다면, 단순히 해당 dom 뒤에 자식 태그를 붙여도 부모태그 내에서만 동작하니까 상관이 없어.
>
> 4. 하지만 Fragment는 부모 태그가 따로 없음에도 자식들의 순서가 내부적으로 정해져야 해. 이때 Fragment를 마운트할때처럼 parentDom에 붙여넣으면 Fragment외의 태그들과 순서가 섞일 수 있으니 주의해야해.
>
> 5. 따라서 여기서 anchor가 필요함. 없는 부모태그를 대신해 위치를 잡아줄 변수야.
>
> 6. 내 추측상 instance는 렌더링되어야할 순서대로 배열에 쌓이게 됨.
>
> 7. 그렇다면 instance 배열 순서를 지키면서 업데이트를 해야함.
>
> 8. 순서를 지키려면... 역순으로 돈다고 했을때도 마지막 태그는 맨 마지막에 넣게 되는거 아냐? (appendChild처럼)

### 사용자의 핵심 질문

- 새롭게 생긴 인스턴스 배열의 순서가 어떻게 정해지는가?
- 이 새로운 인스턴스 배열의 순서대로 가는 것인가?
- 기준이 어떻게 생기는 것인가?
- 역순으로 돌아도 마지막 태그가 맨 마지막에 가는 것 아닌가?

## 이해도 분석

### ✅ 제대로 이해한 부분

#### 1. 재귀적 렌더링 구조
> "모든 렌더링 때마다 처음부터 시작돼. 최상단 부모를 탐색하다가, 자식 태그가 있다면 재귀적으로 호출되는 구조야."

**정확합니다!** reconcile은 트리 구조를 DFS(깊이 우선 탐색)로 순회하며, 각 노드에서 자식들을 재귀적으로 처리합니다.

#### 2. Fragment의 역할
> "Fragment는 여러개의 자식 태그를 가질 수 있어. 하나로 묶는거지."

**정확합니다!** Fragment는 실제 DOM 없이 여러 자식을 그룹화하는 역할입니다.

#### 3. host 요소의 단순한 처리
> "host처럼 부모 태그(=dom)가 명확하게 위치한다면, 단순히 해당 dom 뒤에 자식 태그를 붙여도 부모태그 내에서만 동작하니까 상관이 없어."

**정확합니다!** `<div>` 같은 host 요소는 자체 DOM이 있어서 자식들이 그 안에만 들어가므로 형제들과 섞일 일이 없습니다.

#### 4. Fragment의 특수한 상황
> "Fragment는 부모 태그가 따로 없음에도 자식들의 순서가 내부적으로 정해져야 해. Fragment를 마운트할때처럼 parentDom에 붙여넣으면 Fragment외의 태그들과 순서가 섞일 수 있으니 주의해야해."

**정확합니다!** Fragment의 자식들은 parentDom에 직접 삽입되므로, 다른 형제 요소들과의 순서를 신경써야 합니다.

#### 5. anchor의 필요성
> "따라서 여기서 anchor가 필요함. 없는 부모태그를 대신해 위치를 잡아줄 변수야."

**정확합니다!** anchor는 "여기 앞에 넣어라"는 기준점 역할을 합니다.

#### 6. 인스턴스 배열의 순서
> "내 추측상 instance는 렌더링되어야할 순서대로 배열에 쌓이게 됨."

**정확합니다!** `newInstances` 배열은 **목표로 하는 DOM 순서**대로 정렬되어 있습니다.

### ❌ 잘못 이해한 부분

#### "역순으로 돌아도 마지막 태그가 맨 마지막에 넣게 되는 거 아냐?"

**이 부분이 잘못된 이해입니다.**

역순으로 돌 때:
- 마지막 태그(index가 가장 큰 것)를 **가장 먼저** 처리합니다
- 이 태그를 **맨 뒤에** 배치합니다 (anchor = null)
- 그 다음 앞의 태그들을 순서대로 "방금 배치한 것 앞에" 삽입합니다

결과적으로 **배열 순서대로** DOM이 배치됩니다!

## 핵심 설명

### 📌 1. newInstances 배열의 순서는 어떻게 결정되는가?

**핵심: newChildren(VNode 배열)의 순서를 그대로 따릅니다!**

```typescript
const newInstances = newChildren.map((newChild, index) => {
  const key = newChild.key || String(index);
  const oldChild = oldChildrenMap[key] || null;
  // ...
  return reconcile(dom, oldChild, newChild, childPath);
});
```

#### 흐름 설명

**JSX:**
```jsx
<ul>
  {items.map(item => <li key={item.id}>{item.label}</li>)}
</ul>
```

**items 배열이 바뀌면:**
```javascript
// items = [{id: "a"}, {id: "b"}, {id: "c"}]
// → newChildren = [VNode_A, VNode_B, VNode_C]

// items = [{id: "b"}, {id: "c"}, {id: "a"}]  (재정렬)
// → newChildren = [VNode_B, VNode_C, VNode_A]
```

**reconcileChildren에서:**
```javascript
// newChildren = [VNode_B, VNode_C, VNode_A]
const newInstances = newChildren.map((newChild, index) => {
  // index 0: VNode_B → oldChildrenMap["b"] → B_instance 반환
  // index 1: VNode_C → oldChildrenMap["c"] → C_instance 반환
  // index 2: VNode_A → oldChildrenMap["a"] → A_instance 반환
});
// newInstances = [B_instance, C_instance, A_instance]
```

**결론:** `newInstances`의 순서는 **새로운 VNode 배열(newChildren)의 순서**와 동일합니다. 이것이 바로 **목표 DOM 순서**입니다.

---

### 📌 2. 역순 순회가 올바른 순서를 만드는 원리

**핵심: "뒤에서부터 자리를 확정"하는 전략**

#### 🎯 비유: 줄 서기

5명이 줄을 서야 한다고 생각해보세요: `[철수, 영희, 민수, 지연, 현우]`

**정방향으로 세우면:**
```
1. 철수를 영희 앞에 세워 → 근데 영희가 아직 안 왔음!
   → 기준이 없어서 실패
```

**역방향으로 세우면:**
```
1. 현우를 맨 뒤에 세움 → 현우 위치 확정 ✅
2. 지연을 현우 앞에 세움 → 현우가 있으니 정확한 위치 ✅
3. 민수를 지연 앞에 세움 → 지연이 있으니 정확한 위치 ✅
4. 영희를 민수 앞에 세움 → 민수가 있으니 정확한 위치 ✅
5. 철수를 영희 앞에 세움 → 영희가 있으니 정확한 위치 ✅

결과: [철수, 영희, 민수, 지연, 현우] ✅
```

#### 🔧 코드로 보기

```typescript
// newInstances = [B, C, A] (목표 순서)

for (let i = newInstances.length - 1; i >= 0; i--) {
  const instance = newInstances[i];
  const nextInstance = newInstances[i + 1];
  const anchor = nextInstance ? getFirstDom(nextInstance) : null;
  insertInstance(dom, instance, anchor);
}
```

**실행 과정:**

```
초기 DOM 상태: [A] [B] [C] (원래 순서)
목표:          [B] [C] [A]

i=2: instance=A, nextInstance=undefined, anchor=null
     → A를 맨 뒤에
     DOM: [B] [C] [A]  (A가 이동)

i=1: instance=C, nextInstance=A, anchor=A의DOM
     → C를 A 앞에
     DOM: [B] [C] [A]  (C는 이미 A 앞에 있으므로 이동 없음)

i=0: instance=B, nextInstance=C, anchor=C의DOM
     → B를 C 앞에
     DOM: [B] [C] [A]  (B는 이미 C 앞에 있으므로 이동 없음)

최종: [B] [C] [A] ✅
```

### 📌 3. 왜 "마지막을 먼저 처리"하면 순서가 맞는가?

**핵심: insertBefore는 "앞에 삽입"이므로, 기준점(anchor)이 먼저 있어야 합니다.**

#### insertBefore의 동작

```javascript
parent.insertBefore(newNode, referenceNode);
// newNode를 referenceNode 앞에 삽입
```

- `referenceNode`가 **반드시 존재해야** 합니다
- 역순으로 처리하면 `referenceNode`가 **항상 이미 올바른 위치**에 있습니다

#### 만약 정방향으로 하면?

```
목표: [B, C, A]
초기: [A, B, C]

i=0: B를 C 앞에 넣으려 함
     → 근데 C는 아직 원래 위치(index 2)에 있음
     → B가 A와 C 사이에 들어감
     → [A, B, C] (변화 없음)

i=1: C를 A 앞에 넣으려 함
     → A는 원래 위치(index 0)에 있음
     → C가 A 앞에 들어감
     → [C, A, B]

i=2: A를 맨 뒤에
     → [C, B, A]

결과: [C, B, A] ❌ (목표는 [B, C, A])
```

### 📌 5. getFirstDom으로 순방향을 해결할 수 없는 이유

**질문**: "getFirstDom과 getFirstDomFromChildren을 사용하면 역순 순회를 안 해도 되지 않을까?"

**답변: 아니오, 불가능합니다.**

#### getFirstDom의 역할

`getFirstDom`은 인스턴스에서 **첫 번째 DOM을 찾는 것**일 뿐입니다:

```typescript
export const getFirstDom = (instance: Instance | null): HTMLElement | Text | null => {
  if (!instance) return null;
  if (instance.dom) return instance.dom;
  for (const child of instance.children) {
    if (child?.dom) return child.dom;
  }
  return null;
};
```

이 함수는:
- ✅ 인스턴스에서 첫 번째 DOM 노드를 찾음
- ❌ 그 DOM이 **올바른 위치에 있는지**는 알 수 없음

#### 핵심 문제

순방향에서 `getFirstDom(nextInstance)`를 호출하면, 해당 DOM은 **아직 처리되지 않은 상태**입니다.

```typescript
// 순방향 코드
newInstances.forEach((instance, index) => {
  const nextInstance = newInstances[index + 1];
  const anchor = nextInstance ? getFirstDom(nextInstance) : null;  // ⚠️ 문제!
  insertInstance(dom, instance, anchor);
});
```

**예시: [B, C, A] 재배치**

```
초기 DOM: [A_dom, B_dom, C_dom] (인덱스 0, 1, 2)
목표: [B_dom, C_dom, A_dom]

i=0 (B 처리):
  anchor = getFirstDom(C_instance) = C_dom
  → C_dom은 현재 DOM의 인덱스 2에 있음
  → B_dom을 C_dom 앞에 삽입
  → DOM: [A_dom, B_dom, C_dom]
  → B는 이미 C 앞에 있으므로 이동 없음 (하지만 A가 아직 앞에 있음!)

i=1 (C 처리):
  anchor = getFirstDom(A_instance) = A_dom
  → A_dom은 현재 DOM의 인덱스 0에 있음 (아직 처리 안 됨!)
  → C_dom을 A_dom 앞에 삽입
  → DOM: [C_dom, A_dom, B_dom]

i=2 (A 처리):
  anchor = null
  → A_dom을 맨 뒤에
  → DOM: [C_dom, B_dom, A_dom]

결과: [C, B, A] ❌
```

#### 왜 이런 일이 발생하는가?

**anchor로 사용하는 DOM이 "올바른 최종 위치"에 있어야 합니다.**

- **역순 순회**: anchor(다음 요소)가 이미 처리되어 올바른 위치에 있음 ✅
- **순방향 순회**: anchor(다음 요소)가 아직 처리 안 되어 **원래 위치**에 있음 ❌

`getFirstDom`은 DOM의 **존재**를 찾을 뿐, 그 DOM이 **올바른 위치에 있는지**는 보장하지 않습니다.

#### 결론

```
┌─────────────────────────────────────────────────────────────┐
│ getFirstDom = "인스턴스에서 첫 DOM 찾기"                       │
│                                                             │
│ 순방향 문제 = "찾은 DOM이 올바른 위치에 있지 않음"               │
│                                                             │
│ 역순 순회 = 유일한 해결책 (anchor가 항상 올바른 위치에 있음)     │
└─────────────────────────────────────────────────────────────┘
```

**따라서 `getFirstDom`이나 `getFirstDomFromChildren`을 사용해도 순방향 순회의 근본적인 문제는 해결되지 않습니다. 역순 순회가 필수입니다.**

### 📌 4. 실제 예시: Fragment 포함

```jsx
<div>
  <span>First</span>
  <>
    <p>Fragment Child 1</p>
    <p>Fragment Child 2</p>
  </>
  <span>Last</span>
</div>
```

**Instance 구조:**
```
div (host)
├─ span_First (host)
├─ Fragment
│  ├─ p_1 (host)
│  └─ p_2 (host)
└─ span_Last (host)
```

**실제 DOM:**
```
<div>
  <span>First</span>
  <p>Fragment Child 1</p>
  <p>Fragment Child 2</p>
  <span>Last</span>
</div>
```

**reconcileChildren에서의 newInstances:**
```javascript
newInstances = [span_First, Fragment, span_Last]
```

**위치 조정 시:**
```
i=2: span_Last → anchor=null → 맨 뒤에
i=1: Fragment → anchor=span_Last
     → Fragment의 모든 DOM(p_1, p_2)을 span_Last 앞에
i=0: span_First → anchor=p_1(Fragment의 첫 번째 DOM)
     → span_First를 p_1 앞에
```

Fragment는 실제 DOM이 없지만, `getFirstDom(Fragment)`는 `p_1`을 반환하므로 올바른 anchor를 계산할 수 있습니다!

## 요약

### 질문에 대한 답변

#### Q1: 새롭게 생긴 인스턴스 배열의 순서가 어떻게 정해지는가?

**A:** `newChildren.map()`으로 순회하므로, **새로운 VNode 배열(newChildren)의 순서**를 그대로 따릅니다. 이것이 곧 **목표 DOM 순서**입니다.

#### Q2: 이 새로운 인스턴스 배열의 순서대로 가는 것인가?

**A:** 네, 정확합니다! `newInstances` 배열의 순서가 최종 DOM 순서입니다.

#### Q3: 기준이 어떻게 생기는 것인가?

**A:** 역순으로 처리하면서 **이미 배치된 요소**가 다음 요소의 anchor(기준)가 됩니다.

#### Q4: 역순으로 돌아도 마지막 태그가 맨 마지막에 가는 것 아닌가?

**A:** 네, 맞습니다! 하지만 그게 바로 핵심입니다:
- 마지막 태그를 **먼저 맨 뒤에 배치**
- 그 앞 태그들을 **"방금 배치한 것 앞에"** 차례로 삽입
- 결과적으로 **배열 순서대로** DOM이 완성됨

### 기억할 공식

```typescript
// 마지막부터 처리
for (let i = length - 1; i >= 0; i--) {
  // i번째를 (i+1)번째 앞에 삽입
  // i+1은 이미 올바른 위치에 있음!
  insertBefore(items[i], items[i+1]);
}
```
