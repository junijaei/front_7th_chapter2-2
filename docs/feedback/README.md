# 피드백 문서 작성 가이드 (Claude Code용)

## 문서의 목적

이 문서는 Claude Code가 사용자의 코드에 대한 피드백 문서를 작성할 때 참고하는 규칙입니다.

**핵심 원칙**: 사용자는 완벽한 프로젝트가 아닌 **React 학습**을 목표로 합니다. 피드백은 학습을 돕고 성장을 격려하는 방향으로 작성되어야 합니다.

---

## 파일명 규칙

```bash
date "+%Y%m%d-%H%M"
```

파일명 형식:
```
YYYYMMDD-HHMM-간단한요약.md
```

### 예시
- `20251118-1430-mount함수-구현.md`
- `20251118-1520-reconcile-로직-개선.md`
- `20251119-0900-setup-render-연결.md`

### 규칙
1. **날짜/시간**: `date` 명령어로 현재 시각 가져오기
2. **요약**: 한글 사용, 3-5단어로 간결하게
3. **확장자**: 항상 `.md`

## 작성 원칙

### 1. 톤 & 태도

#### ✅ 해야 할 것
- **긍정적이고 격려하는 톤** 사용
- **구체적인 예시**와 코드 제공
- **"왜?"를 항상 설명**
- Before/After 비교 코드 제공
- 이모지 적절히 사용 (✅ 🤔 💡 ⚠️ 🔥 ⏰ 등)

#### ❌ 하지 말아야 할 것
- "잘못했어요", "틀렸어요" 같은 부정적 표현
- 추상적인 설명만 나열
- 해결책 없이 문제만 지적
- 과도한 이모지 남발
- 너무 긴 설명 (간결함 유지)

### 2. 피드백 구성

#### 잘한 점 (✅)
- **최소 3-5개** 구체적 항목 찾기
- 단순히 "좋아요"가 아닌 **왜 좋은지** 설명
- 코드 조각 인용하여 근거 제시
- 개념 이해도 평가

**예시:**
```markdown
#### 3. 재귀 호출을 올바르게 사용했습니다

```typescript
instance.children = children.map((child) => {
  return reconcile(dom, null, child, childPath);
});
```

자식들도 Instance로 만들기 위해 `reconcile`을 재귀 호출했어요.
이것이 React의 트리 구조를 만드는 핵심입니다!
```

#### 개선할 점 (🤔)

각 항목마다 다음 구조를 따르기:

1. **문제점 제목** + 중요도 표시 (`⚠️ 중요!`, `⚠️ 필수`, `💡 권장` 등)
2. **현재 문제:** 코드 인용
3. **왜 문제인가요?** 근본 원인 설명
4. **해결 방법:** Before/After 비교 코드

**중요도 기준:**
- `⚠️ 중요!` - 코드가 동작 안 함, 치명적 버그
- `⚠️ 필수` - 나중에 큰 문제 발생 가능
- `💡 권장` - 더 나은 방법 제안
- `📝 참고` - 알아두면 좋은 정보

#### 학습 포인트 (💡)

- React/JS 개념과 **코드를 연결**
- 표나 다이어그램 활용
- 비유 사용 (예: "건축가", "설계도" 등)

**예시:**
```markdown
#### 2. path의 중요성

```typescript
// path 구조 예시
"App"                    // 루트 컴포넌트
"App.0"                  // App의 첫 번째 자식
"App.0.Counter"          // 컴포넌트 이름
```

**path가 사용되는 곳:**
1. **Hook state 저장**: `hooks.state.get(path)`
2. **Hook cursor 관리**: `hooks.cursor.get(path)`
3. **컴포넌트 식별**: 어느 컴포넌트를 업데이트할지 결정
```

### 3. 코드 예시 작성

#### 코드 블록 규칙
- 언어 지정: ` ```typescript `, ` ```jsx `
- 주석으로 설명 추가
- Before/After 명확히 표시

```markdown
```typescript
// ❌ 현재: 문제가 있는 코드
const mount = (parentDom, node) => { ... }

// ✅ 개선: path 파라미터 추가
const mount = (parentDom, node, path: string) => { ... }
```
```

#### 긴 코드는 핵심만
- 전체 함수 대신 **핵심 부분만** 인용
- `...`로 생략 부분 표시
- 중요한 라인에 주석 추가

## 특수 상황별 대응

### 사용자가 완전히 틀린 접근을 했을 때

1. **먼저 잘한 점을 찾기** (시도한 것, 생각한 것)
2. **왜 그렇게 생각했는지 이해** 표현
3. **올바른 방향 제시** + 이유 설명
4. **단계별 가이드** 제공

```markdown
### ✅ 잘한 점

시도해본 것 자체가 훌륭합니다! [구체적으로 무엇을 시도했는지]

### 🤔 다른 접근 방법

현재 방식이 작동하지 않는 이유는 [근본 원인]입니다.

React에서는 이렇게 접근합니다:
[올바른 방법 단계별 설명]
```

### 사용자 코드가 거의 완벽할 때

1. 세부적인 개선점 찾기
2. 더 나은 패턴 제안
3. 성능 최적화 팁
4. 다음 학습 단계 제시

### 코드가 미완성일 때

1. 완성된 부분 칭찬
2. 다음에 구현할 부분 힌트
3. 전체 흐름 설명
4. 단계별 TODO 제공

## 문서 길이 가이드

- **짧은 피드백**: 1개 함수, 간단한 수정 → 100-200 줄
- **중간 피드백**: 여러 함수, 개념 설명 필요 → 200-400 줄
- **긴 피드백**: 전체 워크플로우, 복잡한 개념 → 400-600 줄

**원칙**: 필요한 만큼만 작성. 반복은 피하되, 중요한 내용은 충분히 설명.
